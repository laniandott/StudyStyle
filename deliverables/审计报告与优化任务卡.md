## 二、P0 阻断项（数据丢失与安全，均已实测复现）｜ ✅ 已全部修复并回归验证

> **修复状态**：6 条 P0 已于 2026-11-12 全部落地，测试 14 → 32 用例全绿，黑盒验证 5 场景全 PASS。

### P0-1 多设备整库覆盖导致数据静默丢失 ★★★ → ✅ 已修复
- **证据（修复前）**：`server.mjs:85-91` — `PUT /api/store` 直接整库替换，无 merge、无版本号、无冲突检测
- **实测（修复前）**：设备A推3张 → 设备B推5张 → 设备A（本地仍3张）再推一次 → 服务端最终只剩3张，**设备B新增的2张被静默抹除**
- **根因**：客户端 `app.js` 每次 `put()` 都执行一次**全量** `pushServerStore(docs)`；`hydrateFromServerStore` 远端无条件胜出，且只在 `initStore` 执行一次
- **违反**：计划文档第 9 节「两台设备同时修改同一张卡可能产生复制冲突…**不得静默覆盖**」
- **✅ 修复方案**：
  1. 服务端引入库级 `rev`；`PUT` 携带 `base_rev`，不匹配时执行**按 `_id` + `updated_at` 的三方合并**而非覆盖
  2. `createLocalStore.put()` 统一补 `updated_at`（覆盖所有写入路径，含 `saveCard`/`saveReview`）
  3. 客户端跟踪 `serverRev`，合并响应回填本地并提示「已与服务器同步，合并了其他设备的更新」
  4. `pushServerStore` 加 300ms 去抖，消除写放大
- **✅ 回归证据**：设备A写 `[A1]` → 设备B持旧 rev 写 `[A1,B1]` → `merged:true`、count=2、**双方卡片全在**；`tools/blackbox-verify.cjs` 场景 1 PASS

### P0-2 并发写「最后写入者胜出」 ★★ → ✅ 已修复
- **证据（修复前）**：实测 10 个并发 `PUT` 后服务端只剩 **1** 个 doc
- **✅ 修复**：`rev` 乐观锁 + `writeChain` 内原子「读-合并-写」；并发写全部成功且文件保持合法 JSON
- **✅ 回归证据**：`tests/server.test.cjs` 并发写用例 PASS；`tools/blackbox-verify.cjs` 场景 1

### P0-3 非法入参静默清库 ★★★ → ✅ 已修复
- **证据（修复前）**：`server.mjs:87` — `const docs = Array.isArray(body?.docs) ? body.docs : []` 把非法输入**降级为空数组**
- **实测（修复前）**：`PUT {"docs":"不是数组"}` 与 `PUT {}` 均返回 `{"ok":true,"count":0}` 并**清空整个数据库**
- **✅ 修复**：入参严格校验（`docs` 必须为数组、每项须含字符串 `_id`），非法 → **400** 且**绝不调用写入**
- **✅ 回归证据**：`PUT {"docs":"x"}`/`{}`/`{"docs":[{}]}` → 400，**数据量 before=1 after=1 不变**

### P0-4 存储文件损坏被吞后永久覆盖 ★★★ → ✅ 已修复
- **证据（修复前）**：`server.mjs:20-28` — `catch { return []; }` 吞掉 JSON 解析错误
- **实测（修复前）**：截断损坏 → `GET` 返回 `{"ok":true,"docs":[]}` → 任一 PUT 即**永久覆盖**损坏文件
- **✅ 修复**：解析失败 → 重命名备份为 `.corrupt.<ISO时间戳>` + 返回 **500**；**绝不**返回空数组冒充「无数据」；进入「拒绝写入」保护状态，数据可从备份恢复
- **✅ 回归证据**：损坏文件 → 500 + 生成 `.corrupt.*` 备份（**备份内容与损坏原文一致**）+ 再次 GET 仍 500（不返回空数组）

### P0-5 CSRF 跨站清库 ★★★ → ✅ 已修复
- **证据（修复前）**：服务端无 Origin 校验、无鉴权、无 CSRF 防护
- **实测（修复前）**：`POST` + `Content-Type: text/plain`（simple request，**不触发 CORS 预检**）+ 任意 Origin → 直接清空数据库
- **✅ 修复**：同源校验（`Origin` 必须匹配 `Host`）→ 403；可选 `STORE_TOKEN` 令牌鉴权 → 401；`Content-Type` 必须 `application/json` → 415；`POST` → 405
- **✅ 回归证据**：跨源 GET/PUT 均 403、**数据量保持 1 未被清空**；`STORE_TOKEN` 缺/错/对 → 401/401/200

### P0-6 无安全响应头 / 错误码全部伪装为 404 ★ → ✅ 已修复
- **证据（修复前）**：`server.mjs:101-104` — 所有异常被同一个 `catch` 吞成 `404 Not found`
- **实测（修复前）**：非法 JSON → **404**（应 400）；超大 body → **100 Continue**（应 413）；服务端日志**无任何记录**
- **✅ 修复**：分级 400/401/403/404/405/413/415/500（405 带 `Allow` 头）；`console.error` 记录全部异常；补 **6 个**安全响应头（CSP / X-Content-Type-Options / X-Frame-Options / Referrer-Policy / Permissions-Policy）
- **✅ 回归证据**：真实 Chrome 加载页面**零 CSP 违规**，页面完整渲染（说明 CSP 未过严破坏功能）

### P0-9 低分策略 radio 跨卡片状态泄漏 ★★ → ✅ 已修复
- **证据**：原 `updateSchedulePreview`/`saveReview` 读全局 `input[name="lowCycle"]:checked`，而 radio 的 `checked` 属性由上一张卡渲染 → **用户对 A 卡的「重置为 1 天」会被带到 B 卡**

- **Phase 1 需求门禁**：核心算法等价性已验证通过；功能面超出定位的部分**建议沉到二级但不阻塞交付**
